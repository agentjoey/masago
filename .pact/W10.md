## 1. 三种模式 `src/sessions/modes.ts`

按 §2.1–2.3 实现 Conversation / Coach / Challenge。**模式是 session 上的状态**（`sessions.mode` 列 W2 已建），不是每轮参数。

**每种模式的差异必须表达为数据，不是三条代码路径：**

```ts
export interface ModePolicy {
  surfaceAfterTurns: number;        // Conversation 4 / Coach 1 / Challenge 4
  chineseAllowed: 'none' | 'nuance-only' | 'grammar-ok' | 'as-needed';
  hintLadder: boolean;              // Challenge 专有：ヒント 分级提示
  immersive: boolean;               // Challenge：默认全日语
}
export function policyFor(mode: SessionMode, profile: LearnerProfile): ModePolicy;
```

**若你发现必须在 tutor 或 orchestrator 里写 `if (mode === 'CHALLENGE') { ... }` 这类分支来实现核心行为，先停下来在交付说明里提出**——W9 已经证明 Coach 可以只靠阈值参数化，Challenge 大概率也可以。允许的例外是 hint ladder，那确实是 Challenge 独有的**流程**而非参数。

**中文使用策略（§2.5）** 由 `profile.level` × `mode` 共同决定，进 ModePolicy，不要散落在 prompt 字符串里。

## 2. 命令路由 `src/telegram/commands/`

按 §2.4 注册。本任务实现这些：

## 3. Retry 闭环

§2.1 要求「纠正后要求用户用推荐表达重新说一次」。W9 已产出 `requestRetry` 与 `retryEvaluation` 字段，本任务把闭环接上：

- SURFACE 且 `requestRetry` 为真时，记录本轮进入 Retry 等待状态
- 下一轮用户发言时，把待验证的 issue 连同「判断是否改善」的指令给 tutor
- tutor 返回 `retryEvaluation` → 写入 `detected_issues.retry_status`（`SUCCEEDED` / `FAILED`）并产生对应 learning event（`RETRY_SUCCEEDED`）
- **Retry 判定必须落成事件与状态，不能只体现在回复文本里**——§3.7 的 mastery 计算依赖这些事件

## 4. corrections 生产接线

## 6. 测试

- 三种模式各自的 `ModePolicy` 正确；**模式差异不产生独立代码分支**（除 hint ladder）
- Challenge 默认不出现中文；连续失败两次后才给关键词（§2.3 的分级提示）
- `/coach` 立即冲刷 pending，且**同一批 issue 不会被呈现两次**
- `/end` 触发最后一次呈现且 `requestRetry` 为 false（W9 已定的行为）
- Retry 闭环：SURFACE→用户重说→`retry_status` 落库→产生 `RETRY_SUCCEEDED` 事件
- Retry 失败路径同样落库，不产生伪造的成功事件
- 未知命令与未启用命令不触发任何 provider 调用
- 命令消息仍走完整 middleware，**未授权用户发 `/coach` 被静默丢弃**（回归防护 W3 的安全验收项）
- 接线后端到端：连续 4 轮文本对话，前 3 轮无纠错卡、第 4 轮有，且 4 轮的 issue 都在库里
