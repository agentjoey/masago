## 1. OpenAI STT 适配器 `src/speech/stt/openai.ts`

### 已核实的契约

```
POST https://api.openai.com/v1/audio/transcriptions
Authorization: Bearer <OPENAI_API_KEY>
Content-Type: multipart/form-data

form fields:
  file   = <音频二进制>
  model  = <config.stt.model>   例如 gpt-transcribe

响应（默认 json 格式）: { "text": "..." }
```

- **支持格式：`mp3` `mp4` `mpeg` `mpga` `m4a` `wav` `webm`，不含 `ogg`。**
  `supportedInputFormats` 必须**精确**返回这七个，一个不多一个不少——W6 的 normalizer 靠它决定要不要 remux，多写一个 `ogg` 会让整条 R3 修复失效。
- 单文件上限 **25 MB**。
- `STT_CONTEXT_HINTS_ENABLED` 默认为 `false`（§6.1）。**当它为 false 时，不得发送任何 prompt / context / keyword hints 字段。** 这些字段会让模型"按预期猜"，把学习者的语法错误顺手改对，直接污染 Error Bank。这是本产品最不能踩的坑。
- `Transcript.rawText` 取响应的 `text` 字段，**原样保留，不做任何清洗或标准化**。
- usage：OpenAI 按分钟计价，用音频时长填 `audioInputSeconds`（时长由调用方传入，不要试图解析音频）。

## 2. MiniMax TTS 适配器 `src/speech/tts/minimax.ts`

### 已核实的契约

```
POST https://api.minimax.io/v1/t2a_v2
Authorization: Bearer <MINIMAX_API_KEY>
Content-Type: application/json

请求体:
{
  "model": "<speech-2.8-turbo | speech-2.8-hd>",
  "text": "<≤10000 字符>",
  "stream": false,
  "language_boost": "Japanese",
  "voice_setting": { "voice_id": "<MINIMAX_VOICE_ID>", "speed": 1, "vol": 1, "pitch": 0 },
  "audio_setting": { "format": "mp3", "sample_rate": 32000, "bitrate": 128000, "channel": 1 }
}

响应:
{
  "data": { "audio": "<hex 编码的音频>", "status": 2 },
  "extra_info": { "usage_characters": <int>, "audio_length": <毫秒>, "audio_size": <字节>, ... },
  "base_resp": { "status_code": 0, "status_msg": "..." },
  "trace_id": "..."
}
```

### 三个必须处理的坑（照直觉写一定会错）

1. **HTTP 200 不代表成功。** 必须检查 `base_resp.status_code === 0`，非 0 时按失败处理并把 `status_msg` 与 `trace_id` 纳入错误信息。只看 HTTP 状态码会把失败当成功，然后拿着空音频往下走。
2. **音频是 hex 编码**，不是 base64、不是二进制。用 `Buffer.from(data.audio, 'hex')` 解码后写文件。当成 base64 解会得到一堆乱码且不报错。
3. **计费字符数用 `extra_info.usage_characters`**，不要用我们自己 `text.length` 数出来的值。§12.3 明确要求保存供应商返回的 usage；两者可能因文本规范化而不一致，以供应商为准。

其它：
- `outputFormat` 返回 `'mp3'`。
- `audio_length`（毫秒）填入 `AudioResult.durationMs`。
- `text` 超过 `config.tts.maxCharacters` 时**在发送前截断或拒绝**，不要指望供应商侧兜底。

## 4. 通用要求（两个 provider 都适用）

- **超时**：每个 provider 独立超时（§9.3），用 `AbortSignal.timeout()`。
- **重试**：仅对网络超时、429、明确可重试的 5xx 做指数退避 + 随机抖动。**校验失败、401/403、超限、无效音频不重试**——重试只会重复烧钱。
- **API key 绝不进日志或错误信息。** logger 已有脱敏，但不要主动把 key 拼进 message 字符串。
- 保存 provider 的 request id / trace id 供审计（MiniMax 是 `trace_id`，OpenAI 用响应头 `x-request-id`）。
- 失败也要产生 usage record（`success=false` + `error_code`）。
