## 本任务解决什么

这是可行性评审中标记为 **R6** 的设计缺口的落地。原方案里 §2.1 要求「3–5 轮后才反馈」，而 §5.4 让模型每轮都输出 `corrections[]`——两者之间没有交接机制。结果是：要么模型每轮都吐纠正（回到逐句打断，破坏 §2.1），要么指望模型自己「攒着别说」（跨轮必然漂移，而 §15.2 要验收这条）。

**解法是把节奏从模型手里移到程序手里**：模型每轮照常识别问题并全部落库，何时呈现由 Correction Scheduler 按确定性规则决定。这样「3–5 轮后反馈」从 prompt 里的建议变成可配置、可单元测试的行为。

## 1. Correction Scheduler `src/corrections/scheduler.ts`

按 `docs/architecture.md` §5.4 的规则实现。**核心是纯函数决策**，便于穷举测试：

```ts
export type SurfacingDirective =
  | { action: 'HOLD' }
  | { action: 'SURFACE'; issues: PendingIssue[]; requestRetry: boolean };

export function decideSurfacing(input: {
  mode: SessionMode;
  turnsSinceLastSurface: number;
  pending: PendingIssue[];
  explicitRequest: boolean;      // 用户发了 /coach 或 /correct
  sessionEnding: boolean;
  config: SurfacingConfig;
}): SurfacingDirective;
```

**呈现条件（满足任一即 SURFACE）：**

- 自上次呈现以来轮数 ≥ `SURFACE_AFTER_TURNS_*`（Conversation 默认 4，Coach 默认 1）
- pending 中 `importance = HIGH` 的条数 ≥ `SURFACE_HIGH_IMPORTANCE_THRESHOLD`（默认 2）
- 用户显式请求（`/coach`、`/correct`）
- session 即将结束（`/end` 或超时前的总结）

**呈现内容：**

- 按 `importance` × 知识项优先级排序，单次最多 `SURFACE_MAX_ITEMS`（默认 3）
- 未入选项**保留在 pending，可跨 session 累积**——不得因为本次没选中就丢弃

**关键约束：** Coach 模式**不是第二条代码路径**，只是把阈值设为 1。若你发现需要为 Coach 写独立分支，说明抽象错了。

## 2. `detected_issues` 持久化

表 W2 已建（含 `surfaced_at`、`retry_status`、`(turn_id, knowledge_key, original)` 唯一约束）。实现 repository：

## 3. Tutor 输出 schema 扩展

按 §5.4 补齐：

```json
{
  "reply": { "japanese": "...", "translation": null },
  "detectedIssues": [ { "original", "recommended", "reason", "naturalAlternative", "knowledgeKey", "importance" } ],
  "correctionCard": null,
  "retryEvaluation": null,
  "session": { "continue": true }
}
```

**字段职责（这是本任务最容易做错的地方）：**

- `detectedIssues` —— **每轮都输出，无论是否呈现**。程序全部写入 `detected_issues`，`surfaced_at` 置空。这保证 Error Bank 不会因为「本轮不是反馈时机」而丢失证据。
- `correctionCard` —— **仅当输入侧 `action = SURFACE` 时非空**。内容是面向用户的渲染文本。
- HOLD 时模型**不得**在 `reply.japanese` 里夹带纠正——这会绕过整个调度机制。**必须有测试断言这一点。**

## 4. 上下文注入

Context Builder 在组装时附加呈现指令（§5.4）：

```
HOLD    → 模型正常对话，识别到的问题只落库，不在回复中提及
SURFACE → 模型把指定问题渲染成纠错卡，并要求用户重说一次
```

指令进 user 轮或 system 尾部**均可，但不得破坏 system 前缀的字节一致性**——W8 已验证前缀逐字节相同是 prompt cache 生效的前提，这里不能把它破坏掉。

## 5. 测试

**Scheduler（穷举纯函数）：**
- 轮数未达阈值且无其它触发条件 → HOLD
- 轮数达到阈值 → SURFACE
- Coach 模式阈值为 1，第一轮即 SURFACE
- HIGH importance 达 2 条时提前 SURFACE（即使轮数未到）
- 显式请求 → 立即 SURFACE
- session 结束 → SURFACE 剩余项
- 单次最多 3 条；**未入选项仍留在 pending**（断言 pending 数量）
- pending 为空时即使满足轮数条件也不产生空的 SURFACE

**持久化：**
- HOLD 期间识别到的问题**全部落库**且 `surfaced_at` 为空
- 同一 turn 重复处理不产生重复条目（唯一约束）
- `markSurfaced` 后不再出现在 `listPending`

**Tutor：**
- HOLD 指令下 `correctionCard` 为 null，且 **`reply.japanese` 不含纠正内容**（构造一个含明显错误的输入，断言回复里没有出现推荐表达）
- SURFACE 指令下 `correctionCard` 非空且包含被指定的问题
- 两种指令下 **system 前缀仍逐字节一致**（回归防护 W8 的缓存前提）

**接线：**
- 连续 4 轮对话：前 3 轮 HOLD、第 4 轮 SURFACE，且前 3 轮识别的问题都在库里
- 改配置（`SURFACE_AFTER_TURNS_CONVERSATION=2`）后节奏随之改变，**无需改动任何 prompt**——这是 R6 的核心价值，必须有测试证明
